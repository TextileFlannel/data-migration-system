# Интеллектуальная система миграции данных в мультимодельных ИС

Концепт-документ ВКР. Рабочее название системы: **DMS** (Data Migration System),
CLI-утилита `dms`.

> Статус: черновик концепции. Документ фиксирует постановку задачи, метод и
> архитектуру, чтобы от него итеративно двигаться к реализации.

---

## 1. Постановка задачи

**Тема:** разработка интеллектуальной системы миграции данных в мультимодельных
информационных системах.

**Конкретный сценарий (фокус ВКР):** автоматическая миграция из документной СУБД
**MongoDB** в реляционную **PostgreSQL**.

Это гетерогенная миграция *между разными моделями данных* — самый содержательный
случай для темы про мультимодельность. Основная трудность: у MongoDB нет
фиксированной схемы (вложенные документы, массивы, «плавающие» типы полей), а
PostgreSQL требует строгую реляционную схему. Значит, для каждого фрагмента
документа нужно принять **структурное решение**, как представить его в реляционной
модели.

### 1.1. В чём «интеллект»

Ядро новизны — **обучаемая ML-модель, которая принимает решения о переносе**.
Для каждого поля / структуры в документах MongoDB модель предсказывает, как это
поле представить в PostgreSQL. Решения, которые традиционно принимает инженер
вручную или простые эвристики, здесь делает классификатор, обученный на данных.

Ключевые решения, которые надо принять при Mongo → Postgres:

- вложенный объект → отдельная таблица (1:1), набор колонок с префиксом, или `JSONB`;
- массив объектов → отдельная таблица (1:N) со связью `FK`;
- массив скаляров → нативный массив Postgres (`int[]`, `text[]`) или дочерняя таблица;
- полиморфное поле (в разных документах разный тип) → какой тип выбрать, или `text`/`JSONB`;
- разреженное поле (есть в 5% документов) → nullable-колонка или вынос в отдельную таблицу;
- вывод конкретного типа Postgres (`smallint`/`int`/`bigint`/`numeric`/`timestamptz`/`uuid`/`text`);
- обнаружение внешних ключей (ссылки `ObjectId` между коллекциями).

## 2. Метод (ML-постановка)

### 2.1. Выход модели

**Классификатор решения по каждому полю / структуре.** На вход — признаки поля,
на выход — класс представления в PostgreSQL. Задача разбивается на две подзадачи:

**(A) Структурное решение** (мультиклассовая классификация):

| Класс             | Что значит                                               |
|-------------------|----------------------------------------------------------|
| `scalar_column`   | обычная скалярная колонка                                 |
| `new_table_1to1`  | вложенный объект → отдельная таблица 1:1                  |
| `new_table_1toN`  | массив объектов → дочерняя таблица 1:N с `FK`            |
| `array_column`    | массив скаляров → нативный массив Postgres                |
| `flatten`         | объект «сплющить» в колонки родителя с префиксом          |
| `jsonb`           | хранить как `JSONB` (нерегулярная/произвольная структура) |
| `foreign_key`     | поле-ссылка → внешний ключ на другую таблицу              |
| `skip`            | служебное/мусорное поле не переносить                     |

**(B) Выбор типа Postgres** для `scalar_column` (вторая модель или правила):
`smallint` / `integer` / `bigint` / `numeric` / `boolean` / `text` /
`timestamptz` / `uuid` / `jsonb`.

### 2.2. Признаки поля (features)

Считаются **только в Go** — одним и тем же кодом и при сборке обучающего набора, и на
инференсе. Поэтому train/serve skew (расхождение признаков обучения и работы) исключён
by design. Набор:

- `path` — полный путь поля (`address.city`), `depth` — глубина вложенности;
- `presence_ratio` — доля документов, где поле присутствует;
- `is_array`, `avg_array_len`, `max_array_len`;
- доли наблюдаемых BSON-типов: string / int / long / double / bool / date / objectId / object / array / null;
- `type_entropy` — мера полиморфности поля;
- `distinct_ratio`, `cardinality` — уникальность (признак ключа/ссылки);
- `avg_len`, `max_len` для строк; `min`/`max` для чисел (int vs bigint);
- `looks_like_fk` — значение похоже на `ObjectId` и встречается в другой коллекции;
- `name_hints` — имя содержит `id`/`date`/`email`/`count`/…;
- `regex_match` — значения похожи на email / url / uuid / datetime;
- `nested_field_count` — число подполей (для объектов).

### 2.3. Baseline (для сравнения)

Эвристический baseline, с которым честно сравниваем обученную модель:

- скаляр → колонка с типом по доминирующему BSON-типу;
- массив объектов → всегда отдельная таблица;
- вложенный объект → всегда `JSONB` (или всегда отдельная таблица — два варианта baseline).

### 2.4. Метрики

- **Качество классификатора:** accuracy, macro-F1 по классам решений, confusion matrix.
- **Качество итоговой схемы vs эталон:** доля верно восстановленных таблиц и связей,
  число `JSONB`-«заглушек» (меньше при регулярных данных — лучше), степень нормализации.
- Сравнение: обученная модель против baseline по тем же метрикам.

## 3. Данные: синтетическая генерация

Проблема «где взять размеченный датасет» решается **генератором на Python**, который
сам порождает пары (признаки, метка) в любом объёме.

Идея — идти «от эталона»:

1. Задаём **эталонную реляционную схему** из шаблонов предметных областей
   (e-commerce: `users`/`orders`/`products`; blog: `authors`/`posts`/`comments`; и т.п.):
   таблицы, типы колонок, связи `FK`.
2. **Денормализуем** её в MongoDB-документы по случайным стратегиям: встраивание vs
   ссылки, разные доли присутствия полей, полиморфизм, переименования, шум, выбросы типов.
3. При денормализации **сохраняем эталонный маппинг** каждого поля (откуда оно пришло) —
   это и есть метки (`label`).
4. Python сохраняет результат как **сырые документы + метки** (напр. JSONL: сами
   документы и файл с правильным ответом по каждому полю). Признаки из них считает
   уже Go.

Так генератор даёт сколько угодно размеченных данных и полный контроль над
сложностью/вариативностью — сильная часть работы. Деление: **генерация синтетики —
Python; расчёт признаков и сборка `train.csv` — Go**.

## 4. Архитектура

**Python — генерация данных и обучение; Go — всё остальное** (вся боевая система +
расчёт признаков). Признаки считаются **только в Go**, одним кодом и при сборке
обучающего набора, и на инференсе — поэтому расхождения train/serve не возникает.

```
ОБУЧЕНИЕ (один раз, на этапе разработки):

  Python generate ──► сырые документы + метки (JSONL)
        │
        ▼
  Go  build-dataset  (считает признаки) ──► train.csv
        │
        ▼
  Python train ──► models/model.txt (LightGBM)
        │
        ▼
  Python evaluate ──► метрики, сравнение с baseline


РАБОТА (каждая миграция, только Go):

  dms profile ──► dms plan ──► dms migrate ──► dms verify
                    │
                    └─ признаки ──► model.txt (через leaves)

  Признаки в обоих блоках считает ОДИН И ТОТ ЖЕ Go-код.
```

- **Python** отвечает за: генерацию синтетики (документы + метки) и обучение/оценку
  модели (LightGBM, метрики, графики). Результат — файл `models/model.txt`.
- **Go** отвечает за всё остальное: сборку `train.csv` из сгенерированных документов
  (`build-dataset`), профилирование реальной MongoDB, расчёт признаков, инференс
  (через `leaves`), построение плана, создание схемы и перенос в PostgreSQL, верификацию.
- **Признаки — только в Go.** Один и тот же код считает их и при сборке обучающего
  набора, и в бою → модель всегда видит одинаковые числа, отдельная синхронизация не нужна.
- **`leaves`** — чистый Go-ридер моделей LightGBM/XGBoost: загружает `models/model.txt`
  и делает инференс без CGo и без Python.

### 4.1. Этапы работы (pipeline)

**Акт 1 — подготовка модели (Python, один раз на этапе разработки):**

```
python ml/generate.py   # синтетика: сырые документы + метки (JSONL)
dms build-dataset       # документы + метки → признаки (Go) → train.csv
python ml/train.py      # train.csv → models/model.txt (LightGBM)
python ml/evaluate.py   # метрики, сравнение с baseline
```

**Акт 2 — реальная миграция (Go, CLI `dms`):**

```
dms profile   # профилирование коллекций MongoDB → profile.json
dms plan      # profile.json + модель → план миграции (DDL + план переноса), ревью
dms migrate   # создать схему в Postgres и перенести данные по плану
dms verify    # проверка целостности (кол-во строк, контрольные суммы, FK)
```

Шаг `plan` формирует человекочитаемый план (какое поле куда, какие таблицы и связи
создаются) — пользователь может отредактировать его перед `migrate`.

## 5. Структура проекта

```
data-migration-system/
├── cmd/
│   └── dms/                  # точка входа CLI (cobra)
│       └── main.go
├── internal/
│   ├── profiler/             # профилирование MongoDB и JSONL-дампов → FieldProfile
│   ├── features/             # расчёт признаков — для сборки train.csv и инференса
│   ├── dataset/              # сборка train.csv из документов + меток (build-dataset)
│   ├── model/                # загрузка модели и инференс (leaves)
│   ├── planner/              # профиль + предсказания → MappingPlan (DDL + план переноса)
│   ├── migrator/             # выполнение переноса Mongo → Postgres (батчи, трансформации)
│   ├── schema/               # типы: FieldProfile, MappingPlan, PostgresDDL
│   ├── verify/               # проверка целостности после миграции
│   └── config/               # конфиг, строки подключения
├── ml/                       # Python: генерация данных + обучение
│   ├── generate.py           # генерация синтетики → сырые документы + метки (JSONL)
│   ├── train.py              # обучение LightGBM по train.csv → models/model.txt
│   ├── evaluate.py           # метрики, confusion matrix, сравнение с baseline
│   └── requirements.txt
├── models/                   # обученные модели (model.txt) — читает Go через leaves
├── testdata/                 # примеры документов/профилей для тестов
├── go.mod                    # module intelligent-data-migration-system
└── DESIGN.md
```

### 5.1. Зависимости

- **Go:** `cobra` (CLI), `mongo-go-driver` (MongoDB), `pgx` (PostgreSQL),
  `dmitryikh/leaves` (инференс LightGBM), логгер (`slog`/`zerolog`).
- **Python:** `lightgbm`, `scikit-learn`, `pandas`, `numpy`, `matplotlib`
  (генерация данных, обучение, оценка).

## 6. На будущее (необязательные расширения)

### 6.1. Интерактивный режим (REPL) — возможно, появится

Идея: кроме разовых субкоманд (`dms profile`, `dms plan`, …) добавить интерактивную
сессию — запустил `dms` без аргументов, попал в приглашение `dms> ` и работаешь
внутри, держа подключение / профиль / план в памяти (как `psql`, `mongosh`).

**Статус: под вопросом.** Может быть сделан ближе к концу ради удобного демо, а может
и нет. Научной новизны не добавляет — это «витрина» над тем же движком.

Как встроится (гибрид, без дублирования логики):

- запуск `dms` без аргументов → цикл REPL; с аргументами → разовая команда (как сейчас);
- обе «двери» зовут одни и те же пакеты `internal/*`;
- добавляется структура `Session` (живое подключение Mongo, текущий профиль, план):
  в интерактиве состояние живёт в памяти, в разовом режиме берётся из файлов.

Что нужно соблюдать **уже сейчас**, чтобы это осталось дешёвым:

- держать `internal/*` «чистым» — функции принимают вход и возвращают результат,
  не читают файлы и не печатают в консоль; весь ввод-вывод только в `cmd/dms`.
  Тогда интерактивный режим добавляется сверху тонким слоем за несколько часов.
