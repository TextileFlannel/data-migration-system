# TODO — план реализации

Порядок — по зависимостям: сначала «контракты», затем датасет, модель, план,
миграция. Каждая веха заканчивается рабочим срезом, который можно запустить и
проверить. Архитектуру и смысл см. в [DESIGN.md](DESIGN.md).

Правило на всё время: **логика в `internal/*` — «чистая»** (вход → результат, без
чтения файлов и печати внутри), ввод-вывод только в `cmd/dms`.

Легенда: `[Go]` — на Go, `[Py]` — на Python, `[infra]` — инфраструктура.

## Фаза 1. Данные: генерация → train.csv  (веха A)

Цель вехи: `generate.py` → `dms build-dataset` → `train.csv` работает end-to-end.
Без живых БД, без ML.

- [ ] `[Py]` `ml/generate.py`: один шаблон домена (например, e-commerce:
      `users`/`orders`/`products`) + пара стратегий денормализации (встраивание vs
      ссылки). Выдаёт `docs.jsonl` + `labels.json` с эталонными метками.
- [ ] `[Go]` `internal/profiler`: `ProfileJSONL` — прочитать документы из JSONL,
      агрегировать статистику по каждому пути поля в `schema.FieldProfile`.
- [ ] `[Go]` `internal/features`: реализовать `Extract` — посчитать вектор признаков
      из `FieldProfile` (строго по порядку `Names`).
- [ ] `[Go]` `internal/dataset`: `Build` — профиль + метки → строки `(features, label)`
      → записать `train.csv`.
- [ ] `[Go]` юнит-тесты: `features` и `profiler` на маленьких фикстурах в `testdata/`.
- [ ] **Проверка вехи A:** `python ml/generate.py && go run ./cmd/dms build-dataset`
      создаёт непустой корректный `train.csv`.

## Фаза 3. Инференс и план схемы  (веха C)

Цель вехи: `dms profile` + `dms plan` строят реальный `plan.json` из живой MongoDB.

- [ ] `[infra]` поднять локальную MongoDB (`docker-compose`), залить демо-данные.
- [ ] `[Go]` подключить зависимости: `mongo-driver`, `dmitryikh/leaves`.
- [ ] `[Go]` `internal/profiler`: `Profile` — профилирование живой MongoDB (та же
      агрегация, что и в `ProfileJSONL`).
- [ ] `[Go]` `internal/model`: `Load` + `Predict` через `leaves` (загрузка
      `model.txt`, предсказание класса по вектору признаков).
- [ ] `[Go]` `internal/planner`: `Plan` — по каждому полю `features.Extract` →
      `model.Predict` → собрать таблицы, колонки, связи в `schema.MappingPlan`.
- [ ] `[Go]` человекочитаемый вывод плана (что куда, какие таблицы/связи) для ревью.
- [ ] **Проверка вехи C:** `dms profile` → `dms plan` даёт осмысленный `plan.json`.

## Фаза 4. Миграция и проверка  (веха D)

Цель вехи: полный путь `profile → plan → migrate → verify` работает.

- [ ] `[infra]` поднять локальную PostgreSQL (`docker-compose`).
- [ ] `[Go]` подключить зависимость `pgx`.
- [ ] `[Go]` `internal/migrator`: генерация DDL из плана, создание таблиц в Postgres.
- [ ] `[Go]` `internal/migrator`: батчевый перенос документов Mongo → Postgres с
      трансформациями по плану (вложенность, массивы, внешние ключи).
- [ ] `[Go]` `internal/verify`: сверка количества строк, контрольные суммы,
      целостность внешних ключей.
- [ ] **Проверка вехи D:** миграция демо-базы проходит, `verify` подтверждает целостность.
